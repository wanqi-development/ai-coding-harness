## 一、模型配置化：按**智能体**配模型，界面上填、存数据库

- **要解决什么**：现在「某个智能体用哪个模型」是通过**供应商**间接表达的（`llm._ROLE_MODEL_ATTR`
  把角色映射到 `<供应商>_model`，而凭据只在 `.env` 里）—— 想换模型要改文件 + 重启，
  界面上看不到也改不了。目标：**以智能体为键**配置（5 个主控形态：qa / analysis / plan /
  review / coding），每行是一整套连接信息（base_url / model / api_key / 上下文窗口）；
  另外允许**指定一个统一模型**给所有智能体共用。界面上填，本地场景存进业务库。
- **为什么当时不做**：先把方案与决策点定下来（密钥怎么存、跟 `.env` 的优先级、
  保存后什么时候生效、子智能体与兜底归谁），这些都要用户拍。
- **抓手**：
  - 今天 `.env` 的 5 家**仍是「出厂默认」**（qa / analysis → gpt、plan / coding → glm、
    review → kimi、planner → glm、coder → deepseek、reviewer → kimi）—— DB 的行按智能体
    覆盖，**不填就不改行为**，所以是平滑迁移、随时可回退。
  - 合并点只有一处：`Settings` 构造之后套一层 `apply_db_overrides()`；`llm.py` 里
    `_ROLE_MODEL_ATTR` / `_provider_attr` / `_FALLBACK_PROVIDERS` 这三处按
    「角色 → 一行连接」重写（`_main_window` 那条也会跟着变简单）。
  - `sessions` 表本来就存明文 git token，所以「明文存 key」在本地场景不是新增风险类别 ——
    但**词表（`redact.secret_terms`）必须把 DB 来的 key 也纳入**，否则新 key 进不了脱敏词表。
  - 厂商目录（默认 base_url）+ `GET {base_url}/models` 探测（用户点「测试连接」时才发）。
  - 三个归属问题（**待拍**）：① 三个子智能体（planner / coder / reviewer）用哪一行 ——
    推荐跟「coding 主控」那一行（它们只在 coding 形态下被派出去）；② 兜底（主模型重试耗尽后
    换它再试一次）—— 推荐改成**一条独立的「兜底连接」**（留空＝没有兜底），否则「供应商」
    这个概念退不干净；③ 意图分类 —— 推荐仍单独一行（它是技术配置：关思考 + 温度 0，那个键依
    供应商而异），留空则跟统一模型 / qa 行。
- **已定的口径（2026-10-13 用户，逐条）**：
  - 行名用**中文**：问答 / 分析 / 方案 / 审查 / **编码** + 统一模型 / 兜底模型 / 意图识别；
    子智能体（规划 / 编码 / 评审）跟「编码」那一行。

  - **不给默认值**：界面不预填、也不显示「默认是什么」；**哪一行没填就维持今天的行为**

### 1.1 模型**热切换**（已实施到「下一轮生效」这一档）

- 已建的智能体持有的模型实例是长期对象（按 `(会话, 形态)` 缓存）。要让「改了配置立刻对
  运行中的会话生效」得做实例重建 + 并发安全，收益是少一次重启 —— 先不做。
- 中间那一档（**保存后对「新建会话」生效**）留待 1 做完后评估：需要在建智能体那条路径上
  读一次 DB 并做缓存失效，成本比「重启生效」高一点，但体验好很多。

  仍然不做的：**正在跑的那一轮不换模型**（要换得把运行中的图打断重建，收益低、风险高）。

## 二、上下文压缩的口径（计数 + 触发线 + 摘要上限）—— **已实施（2026-10-15，两版）**

> **第一版**：`agent/graph.py` 里把 deepagents 的 `create_summarization_middleware` 工厂换成
> 我们那层壳（`token_counter=cjk_token_counter`，与剪裁同源）—— 上游没暴露这个旋钮，只能换工厂。
>
> **第二版（把第一版换掉了）**：那层壳只解决了「计数口径」，而排查下来真正的三个坑都在
> **上游工厂的默认值**里，且都没暴露成参数（签名只有 `summary_prompt` /
> `trim_tokens_to_summarize` / `token_counter`）—— 于是改成「排掉上游那份、自己构造」：
> `agent/summarization.py`（`HarnessSummarizationMiddleware` + `build_summarization`），
> 排除走 `agent/graph.py` 里 `HarnessProfile.excluded_middleware` 的**按类精确匹配**（所以
> 我们那个子类不会被误伤），挂载位置改到剪裁的**内侧**（上游把它挂在用户中间件外面，
> 它数的是「还没剪的账」）。计数器也换成**中英混合**口径（`context_trim.context_token_counter`）
> —— 统一按 1.6 算时实测把**代码**高估 2.49 倍，而这个上下文里绝大部分是代码。
> 三条根因与取值理由见 CHANGELOG 当日那条。下面这段保留作动机记录。

- **要解决什么**：上游 `SummarizationMiddleware`（deepagents）用
  `count_tokens_approximately`（默认 `chars_per_token=4.0`，英文口径）判断「到没到 85%」。
  中文实测 ≈1.6 字符/token ⇒ **中文上下文被低估约 3 倍**，压缩线实际上打三折才可能触发。
  实测：那几轮输入已经到 110k / 128k（86%）却**一次压缩都没触发**（日志里没有「摘要调用完成」）；
  现在 glm 的窗口按真值改成了 1M，那条线名义上在 892k，实际更不可能到。
- **为什么当时不做**：它会改变**压缩时机**，与「剪历史工具结果」（只改这一次请求、零数据风险）
  的风险面完全不同，混在一起出问题分不清是谁的。
- **抓手**（已按第二版落地）：自己构造那份中间件，`token_counter` 用
  `context_trim.context_token_counter`。**真机那一轮已经看到了**（2026-10-16 查，会话
  `cb4c905c` 23:22:21）：`摘要调用完成：输入 40019 / 输出 3617`，压完第一次模型调用输入
  **38,521**，而上一轮末次是 **152,340**；剪裁那侧的证据是输入曲线出现回落（64,833→62,450
  这种，当时还有常规 40k 剪裁；2026-10-17 已删，现在只有 `CONTEXT_PRETRIM`）。
**2026-10-18 补上了**「估算值与供应商真值差多少」这层校准：`agent/middleware/context_calibration.py`
  按 `(base_url, model)` 做 EMA（α=0.3），样本来自每次调用的 `usage_metadata.input_tokens`，
  只认「刚发出去的那一份」；没有样本时系数 1.0。**还差的**是真机验证 —— 本机 PostgreSQL
  当时未启动，后端没跑；下次起来后看 `CONTEXT_CALIBRATION` 的 `ratio` 是否收敛到实测的
  1.05（deepseek-v4-pro）/ 1.29（deepseek-flash）附近。
- **顺带**：这条与压缩线处的「应急裁剪」是互补的 —— 裁剪管「便宜」（省 token / 省钱），
  压缩管「撑不爆窗口」。

## 二·五、压缩 / 上下文这条线上还没做的几件（2026-10-15 起）

- **摘要正文没过脱敏**：上游 `_acreate_summary` 是直接 `self._summary_model.ainvoke(...)`、
  **不经** handler，于是绕过所有内层中间件 —— 包括我们的 `ModelRedactionMiddleware`。
  摘要文本随后作为一条 `HumanMessage` 进上下文，同一批被逐出的原文还会 offload 到
  `/conversation_history/{thread_id}.md`；这与下面「三」里那条「导出未脱敏」是同一个出口的
  两端。抓手：在 `HarnessSummarizationMiddleware` 里覆写 `_acreate_summary` 给结果过一遍
  `redact`，或在写 offload 前过一遍。**压缩现在真的会触发了**，这条的优先级比之前高。
- **摘要用的是主控自己那个贵模型**：`build_summarization` 收的就是该角色的模型实例
  （触发线要按它的窗口算，所以必须是同一个）。要省钱得单开一条「摘要模型」行 ——
  与「别再堆配置格」的口径冲突，先记着；成本上限已由 `CONTEXT_SUMMARY_INPUT_TOKENS` 兜住。
- **`truncate_args_settings` 与 `CONTEXT_TRIM_CLEAR_INPUTS` 是两套截断**：我们那套默认关
  （「第一版不剪工具入参」），上游这份却是**开着的**（比例线 85% / 保留 20k / `max_length`
  2000，本次照抄了它的默认值）。两者都只改「这一次请求」（`request.override`），所以
  「不动 checkpoint」的保证仍在，但「不剪入参」那句话现在只对剪裁那一套成立 ——
  要么承认这个分工，要么把上游那份也关掉。
- **空转刹车认不出「同一个文件、不同 offset/limit」**（2026-10-16 记，从那次 analysis 触顶
  查出来的）：`LoopGuardMiddleware` 的键是「工具名 + 入参的精确 JSON」，而模型反复读同一个
  文件时每次带的是**不同的分页参数**，于是一轮里读同一个文件 8 次、一次都没被数成重复
  （那轮日志里「本轮已经用同样的参数调用过 N 次」出现 0 次），200 个超级步就是这么烧完的。
  抓手：给「读文件」这一类工具单独定键（只取路径，或路径 + 是否重叠的区间），或者另立一条
  判据「同一文件本轮读过 N 次就先劝一句」。注意别把正常的分段读取（一个大文件分三次读完）
  误判成空转 —— 判据里得有「已经读到过内容」这一层。
  **优先级已降**（同日）：诱因那侧已经断掉了 —— 占位符带身份且不再劝重读、
  当时把保留窗口从 6 抬到 12（该配置 2026-10-17 已随常规剪裁一起作废）、分析形态改成
  「边取证边下结论」（见 CHANGELOG 2026-10-16）。
  这道网是**最后一道**：等真机量一轮，重读次数没降下来再补它。
- **递归上限触顶是抛错、不是收口**（2026-10-16 记）：`AGENT_RECURSION_LIMIT=200` 对
  「分析整个仓库」这类形态偏紧，而触顶时 `GraphRecursionError` 一路抛到 `service.py`
  记成「处理失败」—— 用户拿到的是一句报错，而这一轮已经查到的东西（几十次读文件换来的
  结论）全丢了。抓手：在快到上限时（比如剩 10 步）由中间件注入一句「步数快用完了，
  现在就把已掌握的写成结论」，或者触顶时改为把最后一条 AI 消息当结论收口 + 记一条中断。
  与 `handoff.py` 那个 `recursion_limit` 是同一格配置，两处要一起改。

## 四、意图澄清：margin 先不做（2026-10-19 记）

- **要解决什么**：低置信度澄清目前只看 `confidence < 0.55`；想判断“第一名是否明显领先”
  时，曾考虑加 `top1 - top2` 的 margin。用户 2026-10-19 明确：**先不做 margin**，
  保留为后续候选方案。
- **为什么当时不做**：概率严格归一的前提下，margin 和 top1 强相关：
  `top2 <= 1 - top1`，所以 `margin ∈ [2×top1-1, top1]`。在 0.55 阈值下，
  0.15 / 0.20 的 margin 只能覆盖很窄的区间；JEV 的 confidence 本身还会跨次抖动
  （同一低频样本出现过 0.21 / 0.57），margin 也会跟着抖。与其加一个没验证的旋钮，
  不如先做澄清状态和真实评测。
- **动手时的抓手**：
  - `server/intent.py::should_clarify` / `clarification_decision` 目前只读 confidence；
    `JevDecider` 已经算了次高候选但只写日志，`ParsedReply.candidates` 也已经解析；
  - 先扩展 `scripts/eval_intent.py` 的逐样本 dump，记录 `top1` / `top2` / `margin`，
    再按 confidence/margin 分桶算真实准确率；
  - 只有在样本证明 margin 能把“confidence 过线但实际错”的样本捞出来，且澄清率可接受时，
    才加配置项；否则保持现状；
  - 另一个候选方向是低置信度**双跑一致性**（只在不确定时多判一次），它比 margin
    更能对抗 JEV 抖动，但要单独算成本。
