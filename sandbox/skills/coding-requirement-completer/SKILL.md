# 编码需求补全 Skill

## 1. 作用

接住模糊的编码需求，判断"缺什么、要不要问、问多少"，
补全后产出可直接使用的代码。核心目标：**能猜就猜，猜完给代码；
只在猜错成本高时才追问。**

## 2. 触发条件

用户消息属于以下任一意图，且 **未提供完整实现所需信息** 时启用：
- 写代码（write）
- 改代码（modify）
- 找 Bug（debug）
- 解释代码（explain）
- 重构（refactor）
- 写测试（test）
- 技术选型（choose）

> 若用户需求已足够明确（语言、运行形态、核心逻辑齐全），
> 直接产出，不进入追问流程。

## 3. 执行流程

### Step 1 · 意图识别
判断输入属于哪个意图域：
`write | modify | debug | explain | refactor | test | choose`
无法判断 → 只问一个开放问题："你想让我做什么？"
（例如：写代码 / 查Bug / 解释 / 重构）

### Step 2 · 信息提取
从用户输入中抽取已知槽位：
- language（语言）
- runtime（运行形态：脚本 / CLI / Web API / 库）
- io_spec（输入输出规格）
- core_logic（核心业务逻辑）
- storage（持久化方式）
- scale（规模/性能要求）
- constraints（约束：依赖、版本、环境）

### Step 3 · 复杂度分级  ★核心步骤
依据"完成该任务所需的信息量 + 猜错代价"判定：

| 级别 | 特征                                                       | 处理方式                         |
| ---- | ---------------------------------------------------------- | -------------------------------- |
| 简单 | 单文件、逻辑直白、几行到几十行；语言可默认                 | **不追问** ，直接产出 + 标注假设 |
| 中等 | 单功能/单文件，但关键槽位（语言/运行形态）缺失且猜错代价高 | 追问 ≤3 个槽位                   |
| 复杂 | 多模块、系统级、涉及架构选型                               | **先反问范围级别** ，再追问      |

 **判定原则** ：
- 若"猜错会导致代码几乎白写"（如语言选错、运行形态选错）→ 至少中等，需追问
- 若"猜错只需小改"（如输出格式、变量命名）→ 降级为简单，直接产出
- 预判工作量 >1 个文件或 >100 行 → 视为复杂

### Step 4 · 分层追问

仅对 **中等 / 复杂** 任务执行。按三层取槽位：

 **第一层 · 必问（可枚举 → 给选项）** 
- language：① Python ② JavaScript/Node ③ Java ④ Go ⑤ 其他
- runtime：① 脚本 ② 命令行工具(CLI) ③ Web API/服务 ④ 可复用库 ⑤ 其他

 **第二层 · 该问（半开放 → 选项 + "其他"）** 
- io_spec：① 读文件 ② 读接口/数据库 ③ 用户输入 ④ 其他
- storage：① 不存(仅打印/返回) ② 文件(CSV/JSON) ③ 数据库 ④ 其他
- core_logic：给 2~4 个常见功能点选项 + "其他"

 **第三层 · 默认兜底（不问，直接按最佳实践来，产出一并声明）** 
- 错误处理：默认加基础 try/except
- 参数校验：默认加
- 日志：默认不加或最简
- 测试：默认不写，除非用户提及
- 依赖：默认用标准库 / 最主流库，不引入冷门依赖

 **追问格式要求** ：
- 首轮最多问 3 个槽位
- 选项用 ①②③ 编号，末尾必带"其他"
- 明确告诉用户可一次性回复，如"可回 `1② 2① 3①`"

### Step 5 · 收敛判断（"够用原则"）
满足以下任一，即产出，不再追问：
- 缺口槽位为空
- 剩余缺口可用默认值合理兜底

> 不追求 100% 补全。标准是：**用现有信息 + 合理默认值，
> 能否产出用户大概率能接受的结果。**

产出时 **必须声明所有默认假设** ，例如：
"我默认用 Python + 脚本形态，加了基础错误处理，未加日志和测试。"

### Step 6 · 兜底处理
- 用户选"其他" → 转开放输入
- 用户答非所问 → 纠偏 1 次；二次仍不匹配 → 用默认值执行
- 用户连续跳过/表现不耐烦 → 立即产出 + "事后可调"
- 用户只回部分槽位 → 对剩余槽位用默认值补全，继续产出

## 4. 硬性约束

1.  **简单任务绝不追问。**  追问 = 骚扰。
2.  **追问轮次上限 2 轮** ，2 轮后无论信息是否齐全都必须产出。
3.  **能枚举才给选项，不能枚举一律开放问。**  禁止为不可枚举槽位硬凑选项。
4.  **产出优先于提问。**  编码用户预期是尽快看到能跑的东西。
5.  **所有默认假设必须显式声明** ，不得静默替用户做决定。
6. 追问时 **不打断** ，用编号选项，降低用户回复成本。

## 5. 对话示例

 **示例 A —— 简单，不追问** 
> 用户：写个读取 CSV 并统计行数的脚本
>
> 处理：语言默认 Python，形态为脚本 → 直接产出。
> "默认用 Python，如需其他语言告诉我。"

 **示例 B —— 中等，追问一轮** 
> 用户：帮我写个爬虫
>
> 处理：缺 language / runtime / io_spec → 追问：
> 1. 语言：① Python ② Node.js ③ 其他
> 2. 抓什么：① 静态网页 ② 需登录/动态渲染 ③ API 接口
> 3. 输出：① 存文件 ② 存数据库 ③ 仅打印
> （可一起回，如"1② 2① 3①"）

 **示例 C —— 复杂，先反问范围** 
> 用户：帮我做个用户管理系统
>
> 处理：规模过大 → 先反问：
> ① 最小可运行版（单文件，内存存储）
> ② 完整版（含数据库、API、认证）
> 选①直接开工；选②再对关键点。

 **示例 D —— 兜底** 
> 用户：（被追问后）随便吧
>
> 处理：立即用默认值产出，并声明：
> "按 Python + 脚本 + 标准库 处理，已加错误处理，可后续调整。"

## 6. 输出结构

- [可选] 追问块：编号选项，≤3 项，带"其他"、带一次性回复提示
- [必需] 代码块：可运行
- [必需] 假设声明：用了哪些默认值
- [可选] 调整入口：一句话说明可改哪里
