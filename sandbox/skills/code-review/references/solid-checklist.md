# SOLID 与架构坏味道清单

## SRP（单一职责）

- 一个文件同时承担互不相关的职责（如 HTTP + DB + 领域规则混在一处）
- 类/模块体积大、内聚低，有多个变更原因
- 一个函数编排了许多互不相关的步骤
- 上帝对象：知道系统里过多的事情
- **自问**：「这个模块唯一会因为什么而改动？」

## OCP（开闭原则）

- 新增一种行为需要改一堆 switch/if 分支
- 功能扩展要改核心逻辑，而不是走扩展点
- 没有插件/策略/钩子这类变化点
- **自问**：「我能不改旧代码就加一个新变体吗？」

## LSP（里氏替换）

- 子类里做具体类型判断，或对父类方法直接抛异常
- 重写方法放宽了前置条件、或收紧了后置条件
- 子类忽略或空实现父类行为
- **自问**：「调用方不知情的情况下，我能换成任意子类吗？」

## ISP（接口隔离）

- 接口方法一大堆，实现方多数用不上
- 调用方为了少量需求依赖了很宽的接口
- 接口方法被空实现/桩实现
- **自问**：「每个实现方都用得上所有方法吗？」

## DIP（依赖倒置）

- 高层逻辑依赖具体的 IO、存储、网络类型
- 硬编码实现而非抽象或注入
- 导入链把业务逻辑与基础设施耦合在一起
- **自问**：「不改业务逻辑，我能换掉实现吗？」

---

## 常见代码坏味道（SOLID 之外）

| 坏味道 | 特征 |
|---|---|
| **长函数** | 函数超过 30 行，嵌套多层 |
| **依恋情结** | 方法用别的类的数据比用自己的还多 |
| **数据泥团** | 同一组参数反复成组传递 |
| **基本类型偏执** | 用 str/int 代替领域类型 |
| **霰弹式修改** | 一处改动要跨很多文件 |
| **发散式变化** | 一个文件因许多不相关的原因反复改 |
| **死代码** | 走不到、从没被调用的代码 |
| **投机性泛化** | 为假想的未来需求做抽象 |
| **魔法数字/字符串** | 硬编码值没有具名常量 |

## 重构启发

1. **按职责拆，不按体积拆** —— 小文件也可能违反 SRP
2. **需要时才引入抽象** —— 等第二个用例出现
3. **重构要增量** —— 先隔离行为再搬动
4. **先保行为不变** —— 重构前先补测试
5. **按意图命名** —— 名字难起，多半说明抽象本身不对
6. **优先组合而非继承** —— 继承会带来紧耦合
7. **让非法状态无法表达** —— 用类型约束不变量
