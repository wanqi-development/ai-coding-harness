# 责任闭合卡：跨组件效果的最小证明

只在准备写「保证、自动、重试、补偿、最终一致、不影响」这类跨函数 / 跨模块 / 跨进程效果时读。

## 一张卡只证明一个对象上的一个效果

| 格 | 必须回答 | 可接受证据 |
|---|---|---|
| 对象 / 范围 | 对哪些输入、实体、分支成立 | 参数、类型、过滤与分派条件 |
| 触发者 | 谁、何时触发 | 入口、调用点、订阅、调度配置 |
| 当前选择 | 当前路径怎样选中实现 | DI、factory、router、flag、配置读取 |
| 执行者 | 哪段真实实现产生效果 | 实际 callee 与关键分支 |
| 成功效果 | 成功写了什么、在哪可观察 | 返回值、提交点、持久化、发出的事件 |
| 失败传播 | error 是返回、被检查、被吞还是转成功 | return / continue / callback 分支 |
| 再触发 | 谁保存失败状态并再次触发 | durable state、consumer、scheduler |
| 不覆盖范围 | 哪些对象与副作用不被它修复 | 反例分支与边界 |
| 状态 | 取所有格中最弱的一档 | confirmed / conditional / inferred / unknown |

## 证明规则

- 卡的状态取所有格中最弱的等级。
- 只有实现定义、没有当前选择证据：至多 `conditional`。
- 只有发送 / 调用成功、没有接收与处理证据：不得声称下游效果成功。
- 只有重读或缓存重建：不得声称通知、广播或外部消费得到补偿。
- 没有 durable 失败状态或明确再触发点：不得声称会重试或最终收敛。
- 外部系统行为没有版本化契约或来源完整的观测：标 `unknown`。

## callee 分支门

调用表达式只证明发起了调用；接口名、调用点或返回变量名都不能单独证明 RPC 已发送、数据已持久化、
事务已提交、重试已发生或外部副作用已完成。主张这些效果就继续读实际 callee 与当前装配选择，
把实际存在的分支分别记进证据矩阵：

- `pass-through`：原样返回、转交或仅包装；
- `conditional`：只有特定配置、模式、参数或状态才发生；
- `no-op`：分支明确跳过、短路或不改变相关状态；
- `error`：失败、降级、部分完成、吞错或结果未知窗口。

某类分支不存在时，只能在记录过查询范围后写「该范围内未发现」，不许为填表虚构。

## 反例扫描

签发前搜一遍：early return、ignored error、log-and-continue、best-effort；feature flag、
runtime dispatch、DI / factory 与 no-op 实现；batch 部分完成、重复 / 空输入、幂等键；
事务提交前后与跨存储 / 消息 / RPC 边界；失败记录的保存点、消费者、退避与死信；
相邻但未被当前路径选择的实现。找到反例不等于报告失败 —— 它定义主张的准确范围。
